Git版本管理

2026-04-25
2 minute read
loading... 次

Git 是目前世界上最先进的分布式版本控制系统，几乎是现代软件开发的标配。在这篇博客中，我们将从零开始，带你快速掌握 Git 的核心操作，从创建仓库、代码推送到分支和版本管理。

1. 初始化与配置

在开始使用 Git 之前，建议先配置用户名和邮箱，这会在每次提交记录中显示：

1
2

git config --global user.name "你的名字"
git config --global user.email "你的邮箱@example.com"

创建本地仓库

要在一个新的或者现有的项目中开始使用 Git，你只需在项目根目录运行：

1

git init

这会在当前目录下创建一个隐藏的 .git 文件夹，Git 就是通过它来记录版本历史的。

2. 暂存与提交 (Add & Commit)

Git 的工作流主要包括三个区域：工作区、暂存区 和 版本库。

  1. 查看状态：随时可以使用 git status 看一下哪些文件被修改了。
  2. 添加到暂存区：将修改的文件加入暂存区，告诉 Git 这些是下次要提交的内容。 
    1
2

    git add <文件名>   # 添加指定文件
git add .         # 添加所有已修改的文件
  3. 提交到版本库：为这次更改写一条简短清晰的说明，并保存为一个版本。 
    1

    git commit -m "feat: 初始化项目结构"

3. 连接与推送到远程仓库

本地有了提交记录后，通常我们需要推送到远程平台。

关联远程仓库

如果你在个人远程平台上新建了一个空仓库，可以把它的地址关联到本地：

1

git remote add origin https://github.com/用户名/仓库名.git

(如果是 SSH 方式则是 git@github.com:用户名/仓库名.git)

推送代码

第一次推送并绑定默认分支（通常是 main 或 master）：

1

git push -u origin main

以后只需运行 git push 即可把本地的新提交同步到远程。

4. 版本管理与分支 (Branch)

Git 最强大的功能之一就是分支。它允许你在一条独立的线路上开发新功能，而不影响主代码库。

创建与切换分支 

1
2
3
4
5

git branch feature         # 创建一个名为 feature 的分支
git checkout feature       # 切换到该分支
# 或者使用更现代的命令：
git checkuot feature
git checkuot -c feature      # 创建并直接切换

合并分支 (Merge)

当新功能在分支上开发完成并 commit 之后，我们需要将它合并回主干（main）：

1
2

git checkuot main            # 1. 先切换回主干
git merge feature          # 2. 将 feature 的代码合并进来

5. 模块化开发与代码合并工作流

在实际的项目开发中，我们通常会面临多人协作或者同时开发多个独立功能模块的情况。这时候，**基于分支的模块化开发（Feature Branch Workflow）**就显得尤为重要。

5.1 模块化开发的核心思路

永远不要直接在 main 或 master 主分支上写代码。主分支应该始终保持稳定、可运行的状态。任何新功能、bug 修复，都应该在一个独立的“特性分支（Feature Branch）”上进行，可以维护一个dev分支。

标准开发工作流如下：

  1. 维护dev分支

    1
2
3
4

    git checkout main
git checkout -b dev
git checkout dev
git push -u origin dev

  2. 更新本地主分支：开发新模块前，确保你的本地主干是最新的，避免后续严重的冲突。

    1
2

    git checkuot dev
git pull origin dev

    在此之后更新只需要

    1
2
3

    git add <file_name>
git commit -m "一些简单的描述"
git push

  3. 创建独立的模块分支：为你要开发的新功能创建一个专属分支。推荐使用 feature/ 这样的前缀规范命名。

    1

    git checkuot -c feature/imu_driver

  4. 独立开发与提交：在这个分支上，你可以自由地编写代码、进行多次 git add 和 git commit。这个环境是隔离的，不会影响主干。

  5. 推送到远程：开发完成后，将这个纯粹的模块分支推送到远程仓库。

    1

    git push -u origin feature/imu_driver

5.2 如何管理合并与解决冲突

当一个模块开发并测试完毕后，我们需要将 feature/imu_driver 的代码合并回 main 分支。

  • 团队协作环境：通常不建议直接本地合并。你应该在 GitHub、GitLab 或 Gitee 平台上，基于刚才推送的分支发起一个 Pull Request (PR) 或 Merge Request (MR)。这样可以让同事进行代码审查（Code Review），审核通过后由管理员在网页端合并。
  • 个人开发环境：你可以直接在本地完成合并： 
    1
2

    git checkuot dev
git merge feature/imu_driver

遇到代码冲突（Conflict）怎么办？ 如果不同分支的人恰好修改了同一个文件的同一行代码，Git 会无法自动合并，并提示合并冲突。处理冲突非常简单：

  1. 打开提示冲突的文件，Git 会用 <、=、> 符号标记出两份不同的代码段。
  2. 人工检查并决定保留哪一部分，把 Git 产生的那些冲突标记符号（<<<<<<< 等）删除掉，编写出最终确定的代码。
  3. 告诉 Git 冲突已经解决，并提交： 
    1
2

    git add 冲突的文件
git commit -m "fix: 解决合并时的代码冲突"

这样，你的新模块就被安全且完整地集成进项目主干了！

6. 撤销与历史版本管理

日常开发免不了会出现失误或者需要回退历史版本，常用技巧如下：

  • 撤销工作区修改（还没 add）： 
    1

    git restore <文件名>
  • 查看历史记录： 
    1

    git log --oneline
  • 版本回退 (Reset)（有风险，慎用）： 
    1

    git reset --hard <commit-id>   # 彻底退回到该版本并且丢弃之后的更改
  • 安全撤销历史提交 (Revert)： 用一次新的提交来抵消掉某个历史提交的修改（适合公共分支）： 
    1

    git revert <commit-id>

7. 常见技巧与问题处理

添加了 .gitignore 后，为什么 install/build 等文件夹还是被 push 上去了？

问题原因：.gitignore 只能忽略未被追踪的文件。如果文件或文件夹在添加到 .gitignore 之前就已经被 git add 或者提交进了 Git 仓库，那么即使你后添加了 .gitignore，它们依然会被追踪并 push。

  1. 更新 .gitignore 文件：首先确保在项目根目录的 .gitignore 里忽略了所有的编译输出目录。

    1
2
3
4

    # 在 .gitignore 中添加通配符，忽略所有二级目录下的这三个文件夹
*/install/
*/build/
*/log/

  2. 清除 Git 的缓存记录：使用 git rm --cached 命令可以取消 Git 对这些文件夹的追踪。比如针对你提到的 dev_ws、lidar_ws 和 racing_ws，执行如下命令：

    1
2
3
4
5
6

    # 取消追踪各个工作空间下的具体文件夹
git rm -r --cached <path_to_file>

# 或者直接清空所有暂存区缓存，然后重新所有的 add
# git rm -r --cached .
# git add .

  3. 提交并推送变更：告诉 Git 记录上述更改，推送到远程仓库。

    1
2

    git commit -m "清除install文件"
git push
