ROS2 竞赛现场 DDS 干扰与 RDK X5 通信优化记录

多队同网段调车时，FastDDS discovery、RViz 大话题订阅和 RDK X5 内存压力叠加导致 Bad alloc、CLI 卡死、OOM 的排查与优化记录

2026-07-08
3 minute read
loading... 次

背景

这次问题出现在 OriginCar 实车联调阶段。

平台：

  • RDK X5，约 6.5GiB RAM
  • ROS2 Humble
  • FastDDS
  • 两块 RDK + 一台 PC 参与调试
  • 比赛现场可能有多队同时接入同一局域网

症状不是单一 bug，而是几类压力叠在一起：

  1. ros2 topic hz /odom_combined 一运行，已有节点打印 ParticipantEntitiesInfo_ 反序列化异常和 Bad alloc。
  2. ros2 topic list / ros2 topic hz 偶发卡死。
  3. 建图时 /map topic 存在但没有数据，TF 树不完整。
  4. 一开 PC RViz 或 slam_toolbox，RDK X5 内存快速逼近上限，严重时触发 OOM Killer。

关键日志：

1
2

Fast CDR exception deserializing message of type rmw_dds_common::msg::dds_::ParticipantEntitiesInfo_
'Bad alloc' exception deserializing message ... ParticipantEntitiesInfo_

以及：

1
2

Out of memory: Killed process ... (ekf_node)
anon-rss:1299348kB

第一层原因：DDS discovery 干扰

ROS2 CLI 工具本身也是一个 DDS participant。

所以运行：

1

ros2 topic hz /odom_combined

不是一个“纯本地查看命令”，它会加入 DDS discovery。如果场地里很多队伍处在同一局域网、默认 Domain 0、默认 multicast discovery，那么它会发现其它队伍的 participant。

队伍越多，discovery 数据越复杂，RDK X5 上就越容易出现：

  • ParticipantEntitiesInfo_ 反序列化异常
  • Bad alloc
  • CLI 卡死
  • 节点启动内存尖峰

最基础的隔离是所有本车设备使用同一个独立 Domain：

1
2

export ROS_DOMAIN_ID=42
ros2 daemon stop

注意：改 ~/.bashrc 后，旧终端和 ros2 daemon 不会自动刷新，所以每个终端都要确认：

1
2

echo $ROS_DOMAIN_ID
ros2 daemon stop

第二层原因：每个 ROS2 进程都是内存和 discovery 成本

一开始 slim_bringup.launch.py 里有 3 个独立的 static_transform_publisher：

1
2
3

base_footprint -> base_link
base_footprint -> gyro_link
base_link -> laser

理论上静态 TF 很轻，但在现场日志里，多个 static_transform_publisher 进程也被 DDS 和内存压力放大。

优化方式是合并为一个 C++ 节点：

1

origincar_static_tf_node

它一次性发布三条静态 TF。这样少两个 ROS2 进程，也少两个 DDS participant。

第三层原因：RViz 默认订阅大话题会压垮 X5

PC RViz 看起来运行在 PC 上，但只要它订阅 /scan、costmap、TF、map，X5 和网络都要参与数据分发。

实测中，一开 PC RViz，RDK X5 内存会接近：

1

6.3Gi / 6.5Gi

所以我做了一个轻量 RViz 配置：

1
2

rviz_mapping_light.rviz
rviz_mapping_light.launch.py

默认只看：

  • Map
  • TF
  • Odometry

默认不订阅 /scan。需要检查雷达时，再手动打开 LaserScan 显示。

第四层原因：EKF + SLAM + Nav2 峰值叠加

ekf_node 被 OOM Killer 杀死时，日志里看到 RSS 接近 1.3GB。单看 EKF 算法本身不应该这么高，这说明当时是：

  • DDS discovery
  • 多进程 participant
  • RViz 远程订阅
  • LiDAR
  • SLAM
  • Nav2
  • CLI 工具

共同把系统推到了内存上限。

因此优化不是只改一个参数，而是同时降载：

  1. EKF 降低队列和等待时间，避免 TF wait 阻塞更新循环。
  2. LiDAR 和 SLAM 最大量程限制为 6m，贴合 5m x 5m 场地。
  3. MPPI 降低采样规模和频率。
  4. Planner 降低搜索量和缓存窗口。
  5. local costmap 使用 odom_combined，避免 AMCL 尚未发布 map -> odom_combined 时 controller activation 卡住。

FastDDS Discovery Server 流程

只设置 Domain 还不够稳时，可以让一台 RDK 作为 discovery server。

RDK-A：

1
2

source /root/dev_ws/install/setup.bash
/root/dev_ws/install/origincar_base/lib/origincar_base/start_fastdds_discovery_server.sh 192.168.3.20 11811

所有 RDK 和 PC 终端：

1
2
3

source /root/dev_ws/install/setup.bash
source /root/dev_ws/install/origincar_base/lib/origincar_base/setup_fastdds_discovery_client.sh 192.168.3.20 11811 42
ros2 daemon stop

脚本会设置：

1
2
3

export ROS_DOMAIN_ID=42
export RMW_IMPLEMENTATION=rmw_fastrtps_cpp
export ROS_DISCOVERY_SERVER=192.168.3.20:11811

如果本机有 /root/fastdds.xml，也会继续使用它来禁用共享内存传输。

无 EKF 建图 fallback

如果建图阶段 EKF 仍然导致 OOM，可以临时绕开 EKF：

1
2

/odom -> odom_tf_node -> TF: odom -> base_link
/scan -> slam_toolbox

启动：

1

ros2 launch origincar_base slam_mapping_no_ekf.launch.py start_base:=false

这个方案的定位：

  • 适合低负载建图。
  • 不作为正式导航首选。
  • 正式导航仍优先验证 EKF + AMCL。

在 5m x 5m 小场地内，如果车速低、地面不打滑、外墙 scan 特征足够，无 EKF 建图通常可以接受。

最终推荐启动顺序

RDK-A：

1
2
3
4

source /root/dev_ws/install/setup.bash
source /root/dev_ws/install/origincar_base/lib/origincar_base/setup_fastdds_discovery_client.sh 192.168.3.20 11811 42
ros2 daemon stop
ros2 launch origincar_base slim_bringup.launch.py

RDK-B：

1
2
3
4

source /root/lidar_ws/install/setup.bash
source /root/dev_ws/install/origincar_base/lib/origincar_base/setup_fastdds_discovery_client.sh 192.168.3.20 11811 42
ros2 daemon stop
ros2 launch lslidar_driver lsn10_launch.py

RDK-B 启动建图：

1
2

source /root/dev_ws/install/setup.bash
ros2 launch origincar_base slam_mapping.launch.py start_base:=false

PC 轻量 RViz：

1
2
3

source setup_fastdds_discovery_client.sh 192.168.3.20 11811 42
ros2 daemon stop
ros2 launch origincar_base rviz_mapping_light.launch.py

结果

这次优化后的阶段结果：

  • /odom、/imu/data_raw、/odom_combined、/scan 和基础 TF 链都曾恢复数据。
  • 合并静态 TF 后减少了 ROS2 进程数和 DDS participant 数。
  • 轻量 RViz 避免了 PC 一连接就默认拉 /scan，明显降低调试压力。
  • 无 EKF 建图链路比 EKF + RViz 全开更稳，可作为现场 fallback。
  • QR BPU 侧也同步改为最小 launch，减少 websocket/debug image 等无关网络流量。

还没完全结束的问题：

  • 需要在真正多队同网段环境里继续压测 Discovery Server。
  • 需要长时间观察 RDK X5 是否还会 OOM。
  • 需要复核裁剪地图和路径点坐标。

教训

  1. ROS2 CLI 不是“无副作用观察器”，它也是 DDS participant。
  2. 嵌入式平台上，少一个 ROS2 进程就是少一个 discovery 和内存峰值来源。
  3. RViz 的订阅内容比“RViz 在哪台电脑运行”更重要。
  4. 先把通信和内存稳定住，再调 EKF/SLAM/Nav2 参数，否则现象会互相污染。
  5. 比赛现场不要依赖默认 Domain 0 和默认 multicast discovery。
