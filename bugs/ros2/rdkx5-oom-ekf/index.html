RDK X5 启动 ROS2 节点被 OOM Killer 杀死

free -h 显示内存充足，但 ROS2 节点启动后仍被 OOM Killer 杀死的排查过程

2026-07-05
2 minute read
loading... 次

平台

  • RDK X5 (arm64, 6.5GB RAM)
  • ROS2 Humble
  • OriginCar

问题描述

在 RDK X5 上通过 ros2 launch origincar_base origincar_bringup.launch.py 启动底盘节点时，所有节点在几秒内全部被杀死，exit code 为 -9：

1
2
3

[ERROR] [imu_filter_madgwick_node-6]: process has died [pid 4641, exit code -9]
[ERROR] [origincar_base_node-1]: process has died [pid 4629, exit code -9]
[ERROR] [static_transform_publisher-3]: process has died [pid 4633, exit code -9]

但此时 free -h 显示内存剩余超过 4GB，看起来内存是足够的：

1

Mem:   6.5Gi    1.9Gi    3.9Gi    8.0Mi    772Mi    4.5Gi

排查过程

1. 确认是 OOM Killer

通过 dmesg 查看内核日志，发现明确的 OOM kill 记录：

1
2

oom-kill:constraint=CONSTRAINT_NONE,task=origincar_base_,pid=13238
Out of memory: Killed process 13238 (origincar_base_) total-vm:2149180kB, anon-rss:1452300kB

origincar_base_node 在 launch 过程中瞬间吃到了 1.4GB 内存，但单独运行时只有 23MB。

2. 排除节点本身内存泄漏

单独运行底盘节点，并持续观察内存：

1
2

ros2 run origincar_base origincar_base_node &
while true; do ps -p $(pgrep origincar_base) -o rss=,vsz=; sleep 10; done

输出稳定在 ~22MB，无泄漏：

1
2
3

22608 633976
22608 633976
22608 633976

单独运行没问题，launch 启动就 OOM，说明问题不在节点代码本身。

3. 找到真正原因：后台进程 + launch 集中拉起

查看后台进程内存占用：

1

ps aux | awk '{print $6, $11}' | sort -rn | head -10

发现后台静默运行着大量进程：

进程 内存
vscode-server ×3 538 MB
openclaw-gateway 286 MB
aurora930 深度相机驱动 91 MB
qr_bpu_detector 85 MB
websocket 58 MB

后台已占用超过 1GB，加上 launch 一把梭同时拉起：

  • robot_state_publisher（加载 URDF）: ~342 MB
  • imu_filter_madgwick: ~342 MB
  • ekf_node + DDS 发现 + params 处理: 数十 MB

所有节点的启动内存尖峰叠加，瞬间突破了系统可用内存，触发 OOM Killer。

4. free -h 为何显示内存充足

free -h 是持续测量值，显示的是稳态内存。而 OOM 发生在节点启动的瞬间尖峰——多个进程同时申请内存，尖峰叠加超过阈值，OOM Killer 来不及等它们释放就动手了。

解决方案

方法一：清理后台进程

关闭 VS Code Remote 连接（释放 ~538MB）：

在 Windows 端断开远程连接，或在 RDK X5 上：

1

killall node

禁用 openclaw-gateway（一个 npm 全局包，部署官方RDK Claw是自动部署的服务，占用 ~286MB）：

1
2
3
4
5
6

systemctl --user stop openclaw-gateway
systemctl --user disable openclaw-gateway
rm ~/.config/systemd/user/openclaw-gateway.service
systemctl --user daemon-reload
npm uninstall -g openclaw
rm -rf ~/.openclaw

方法二：精简 launch 文件

原始 origincar_bringup.launch.py 拉起了 robot_state_publisher 和 joint_state_publisher，加载完整 URDF 需要 ~342MB，而 EKF 验证完全不需要 URDF。

新建 slim_bringup.launch.py，去掉不必要的节点：

1
2
3
4
5
6
7
8
9

# 去掉：
# - robot_state_publisher（加载URDF，342MB）
# - joint_state_publisher
# - imu_filter_madgwick（EKF 可直接读 /imu/data_raw）

# 只保留：
# - origincar_base_node（底盘驱动）
# - static_transform_publisher ×3（TF）
# - ekf_node（融合定位）

方法三：去掉 imu_filter_madgwick

原来的配置是：

1

/imu/data_raw → imu_filter_madgwick → /imu/data → EKF

查看 ekf.yaml，发现 EKF 的 imu0 配置已经直接指向 /imu/data_raw，madgwick 这一层完全是多余的，删掉省 350MB：

1
2
3
4

imu0: /imu/data_raw
imu0_config: [false, false, false,
              false, false, true,
              ...]

教训

  1. free -h 不能代替 dmesg：内存充足不等于不会 OOM，要看瞬间尖峰，dmesg | grep oom-kill 才是最终答案。

  2. launch 文件里的节点越少越好：调试阶段没必要把所有节点全拉起来，按需启动，用最小集验证当前目标。

  3. 后台进程是隐形杀手：vscode-server、各类 AI 助手 gateway 等开发工具在嵌入式平台上会悄悄吃掉几百 MB，调试时务必确认后台干净。

  4. exit code -9 不一定是 OOM：也可能是 segfault、权限问题等，要先用 dmesg 确认是 oom-kill 再对症下药。
