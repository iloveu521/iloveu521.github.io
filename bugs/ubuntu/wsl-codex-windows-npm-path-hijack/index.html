修复 WSL Codex 更新被 Windows npm 路径劫持

WSL 中运行的是 Linux Codex，更新命令却落到 Windows npm，导致升级了另一套安装。记录如何沿符号链接、PATH 和 codex doctor 定位混用，并用 WSL NVM 的 npm 完成修复。

2026-10-13
3 minute read
loading... 次

问题现象

在 WSL 中运行 Codex CLI 时，模型和功能看起来比 Windows 侧少。进一步检查还发现一个更直接的问题：Codex 已经落后于当前 npm 包版本，但执行常规更新后，WSL 中实际运行的版本没有变化。

表面上，node、npm 和 codex 都能正常执行：

1
2
3

node --version
npm --version
codex --version

然而它们不一定来自同一套运行环境。WSL 可以通过互操作机制直接调用 Windows 可执行文件；如果 Windows Node.js 路径进入了 WSL 的 PATH，就可能出现“Linux Codex 配 Windows npm”的混合状态。

环境信息

  • Windows 主机中的 WSL2
  • Ubuntu 22.04
  • Zsh 与 NVM
  • Node.js 22
  • Codex CLI 通过 npm 管理
  • WSL 和 Windows 均存在 Codex CLI

本次排查中，WSL 实际运行的是 Linux Codex 0.145.0，npm 包目录返回的目标版本为 0.162.1。版本号只是当时的现场信息，后续排查应以当前包目录为准。

错误信息

codex doctor 给出的关键提示是：

1
2

npm install -g @openai/codex would update a different install
update would target a different npm install

诊断信息同时显示：

1
2

running package root: ~/.nvm/versions/node/<version>/lib/node_modules/@openai/codex
npm package root: Windows npm global directory

也就是说，当前 codex 属于 WSL NVM，但当前命令环境里的 npm 却指向 Windows。

排查过程

1. 不要只看版本，先查命令来自哪里 

1
2
3

type -a codex
which -a node npm npx codex
readlink -f "$(command -v codex)"

codex 的解析链最终进入：

1

~/.nvm/versions/node/<version>/lib/node_modules/@openai/codex

继续检查底层文件：

1
2
3

file ~/.nvm/versions/node/<version>/lib/node_modules/@openai/codex/\
node_modules/@openai/codex-linux-x64/vendor/\
x86_64-unknown-linux-musl/bin/codex

结果是 Linux ELF，而不是 Windows PE 可执行文件。这证明 WSL 当前运行的是独立的 Linux Codex，不是通过 WSL 互操作调用 Windows codex.exe。

2. 对比交互式与非交互式 Shell

直接从 Windows 调用非交互式 WSL：

1

wsl.exe -d Ubuntu -- which -a node npm npx codex

此时 node 和 codex 可以落到 WSL，npm、npx 却可能落到挂载的 Windows 路径。

再通过交互式 Zsh 检查：

1

zsh -lic 'whence -va node npm npx codex'

交互式 Zsh 会加载 NVM，因此 WSL NVM 的 npm 排在 Windows npm 之前。两次结果不同，说明问题不是包本身损坏，而是 Shell 初始化方式改变了 PATH 顺序。

3. 让 Codex 自己检查安装链 

1

codex doctor

相比只运行 codex --version，doctor 会同时核对：

  • 当前 Codex 包根目录；
  • npm 全局包根目录；
  • 实际可执行文件；
  • 登录与配置；
  • 网络连通性；
  • 更新命令将要修改的目标。

本次正是它明确指出“更新会修改另一套安装”，避免了继续反复更新 Windows 包。

根本原因

WSL 与 Windows 各自存在一套 Node.js/Codex，同时 Windows 的可执行文件目录被加入了 WSL 的 PATH。

在交互式 Zsh 中，NVM 初始化会把 WSL 的 Node.js 工具放到前面；但从 Windows 直接启动的非交互式 WSL 命令不会完整加载相同的 Shell 初始化文件，于是发生了这组错配：

1
2

codex -> WSL NVM 中的 Linux Codex
npm   -> Windows Node.js 的 npm

因此，普通的全局安装命令虽然成功退出，修改的却是 Windows npm 全局目录，WSL 正在执行的 Codex 仍停留在旧版本。

解决方案

1. 更新前确认 npm 属于 WSL

在正常的 WSL 交互式 Shell 中执行：

1
2
3
4

command -v node
command -v npm
command -v codex
npm config get prefix

这些路径应当指向 WSL 文件系统中的同一套 NVM 安装，而不是 /mnt/c、/mnt/d 等 Windows 挂载路径。

2. 使用明确的 WSL npm 更新

如果当前非交互式环境的 PATH 不可信，可以直接调用 NVM 安装目录中的 npm：

1

~/.nvm/versions/node/<version>/bin/npm install -g @openai/codex@latest

也可以明确启动会加载 NVM 的交互式 Zsh：

1

zsh -lic 'npm install -g @openai/codex@latest'

这里没有删除 Windows Codex，也没有把 Linux codex 强行替换成 Windows codex.exe。对于需要直接操作 WSL 工作区、Linux 工具链和权限模型的场景，保留原生 Linux Codex 更稳定。

3. 长期修正 PATH 顺序

应确保 Shell 初始化完成后，WSL NVM 的 bin 位于 Windows Node.js 路径之前。自动化脚本如果不加载交互式 Shell，不要假设 npm 与终端中看到的是同一个命令；应使用绝对路径或显式加载 NVM。

验证结果

更新后依次检查：

1
2
3
4
5

codex --version
type -a codex
type -a npm
file "$(readlink -f "$(command -v codex)")"
zsh -lic 'codex doctor'

本次验证结果：

  • WSL Codex 从 0.145.0 更新到 0.162.1；
  • codex 与 npm 在交互式 Zsh 中都优先解析到 WSL NVM；
  • 底层 Codex 仍为 Linux x86_64 ELF；
  • 原有 /usr/local/bin/codex 链接继续指向更新后的 WSL NVM 包；
  • ChatGPT 登录、WebSocket 和 HTTP 服务可达；
  • codex doctor 最终为 0 fail。

更新诊断仍可能因为版本探测端点返回 HTTP 403 而显示非阻塞警告。只要 npm 包目录已确认目标版本、实际安装版本一致，且其余自检通过，就应将它与安装路径错误分开判断。

经验总结

  1. WSL 能运行 Windows 命令，不代表当前命令一定属于 Windows；必须沿 type、which、readlink 和 file 追到最终二进制。
  2. “npm 安装成功”只证明某个全局目录被修改，不证明正在运行的 Codex 被更新。
  3. 交互式和非交互式 Shell 的 PATH 可能不同，NVM、pyenv、conda 等版本管理器都存在同类风险。
  4. 同一工具在 Windows 与 WSL 各装一份时，应同时核对包根目录、包管理器前缀和可执行文件格式。
  5. codex doctor 比单独检查版本更适合诊断安装链、认证、网络和更新目标。
