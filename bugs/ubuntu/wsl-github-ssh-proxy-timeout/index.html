WSL2 里 GitHub SSH 再次超时：这次凶手是 OpenSSH 根本不认识 http_proxy

楔子：同一个报错，不同的凶手 

1

ssh -T git@github.com

1

ssh: connect to host github.com port 22: Connection timed out

熟悉的超时，熟悉的配方。几个月前我刚写过一篇排查记录，那次的结论是 Windows 代理没开「允许局域网访问（Allow LAN）」。

于是我熟练地打开代理软件——Allow LAN 好好开着；又熟练地去 curl 了一下 GitHub——HTTP 200，秒开。

网络是通的，代理是通的，只有 SSH 在装死。

那一刻我意识到：同一个报错，这次换了个凶手。

第一章：现场勘查

1.1 当前环境 

1
2
3
4

Windows 11
├── WSL2：Ubuntu-24.04
├── .wslconfig：networkingMode=mirrored（镜像网络模式）
└── 代理软件：监听 127.0.0.1:7892

注意 networkingMode=mirrored，这是本次破案的关键背景，后面要考。

1.2 第一轮取证

在 WSL 里看默认路由、代理环境变量和 SSH 配置：

1
2
3

ip route | grep default
env | grep -i proxy
cat ~/.ssh/config

结果：

1
2
3
4
5
6
7
8

default via 192.168.0.1 dev eth2

https_proxy=http://127.0.0.1:7892
HTTPS_PROXY=http://127.0.0.1:7892
http_proxy=http://127.0.0.1:7892
HTTP_PROXY=http://127.0.0.1:7892

# ~/.ssh/config —— 不存在

shell 里代理变量一应俱全，但 ~/.ssh/config 根本不存在。

1.3 连通性三连测

测试 命令 结果
走代理访问网页 curl -x http://127.0.0.1:7892 https://github.com ✅ HTTP 200，3.4s
直连 22 端口 </dev/tcp/github.com/22 ❌ 超时
直连 443 备用端口 </dev/tcp/ssh.github.com/443 ❌ 同样超时

结论很清晰：

  1. WSL → Windows 代理 → GitHub 这条链路是通的；
  2. 不走代理的直连，22 和 443 全部被掐死；
  3. 所以 SSH 必须走代理，但它现在显然没走。

上一篇笔记里「改 ssh.github.com:443 就能绕过去」的办法，这次也失效了——443 直连一样超时。

第二章：真相大白

2.1 一个反直觉的事实

很多人（包括我）下意识地以为 shell 里既然设了：

1

export https_proxy=http://127.0.0.1:7892

那所有程序都会乖乖走代理。

并不是。 http_proxy / https_proxy 只是一个「君子协定」：只有主动读取这些环境变量的程序才会遵守，比如 curl、wget、git 的 HTTP 传输。

而 OpenSSH 根本不读这些变量。它既不认识 http_proxy，也没有「HTTP 代理」这个概念。SSH 想走代理，只有一条路：在 ~/.ssh/config 里写 ProxyCommand，外挂一个程序把 TCP 流量搬进代理隧道。

于是案发过程完整了：

1
2
3
4
5
6
7

curl https://github.com
  → 读取 https_proxy → 走 127.0.0.1:7892 → 通 ✅

ssh -T git@github.com
  → 不看任何代理环境变量
  → 裸连 github.com:22
  → 被墙 → Connection timed out ❌

2.2 为什么这次不是 Allow LAN？

上一次事故的前提是 WSL2 的 NAT 网络模式：WSL 住在一个 172.x 的虚拟子网里，访问 Windows 必须走主机网关 IP，而代理只监听 127.0.0.1，所以需要开 Allow LAN 让代理接受局域网连接。

而这次 .wslconfig 里写的是：

1
2

[wsl2]
networkingMode=mirrored

镜像模式下 WSL 直接共享 Windows 的网络栈，WSL 里的 127.0.0.1 就是 Windows 的 127.0.0.1。证据就是前面的 curl——WSL 访问 127.0.0.1:7892 直接拿到了 HTTP 200，根本没碰 Allow LAN。

经验主义害死人。上次的答案没错，但题目已经换了。

第三章：修复

3.1 用 netcat 当代理搬运工

Ubuntu 自带 netcat-openbsd，它支持 HTTP CONNECT 代理（-X connect），不用再装 ncat、corkscrew：

1
2

dpkg -l | grep netcat
# netcat-openbsd

新建 ~/.ssh/config：

1
2
3
4
5

Host github.com
    HostName ssh.github.com
    Port 443
    User git
    ProxyCommand nc -X connect -x 127.0.0.1:7892 %h %p

含义：

  • HostName ssh.github.com + Port 443：GitHub 官方的 443 端口 SSH 入口，比 22 更不容易被针对；
  • ProxyCommand nc -X connect -x 127.0.0.1:7892 %h %p：让 SSH 先连上本机代理，由代理向目标发起 HTTP CONNECT 隧道；
  • Host github.com 保持不变，所以仓库 remote 地址 git@github.com:... 一个字都不用改。

记得给配置文件正确的权限：

1

chmod 600 ~/.ssh/config

3.2 先验证隧道，再验证认证

不放心可以先单独验证代理隧道能不能收到 GitHub 的 SSH 握手横幅：

1

nc -X connect -x 127.0.0.1:7892 ssh.github.com 443 < /dev/null

1

SSH-2.0-20b2056

能看到 SSH-2.0- 开头的横幅，说明隧道已经通到 GitHub 的 SSH 进程了。

然后正式测试：

1

ssh -T git@github.com

1
2

Hi iloveu521! You've successfully authenticated,
but GitHub does not provide shell access.

收工。

小提示：ssh -T 成功时退出码也是 1，这是 GitHub 的正常行为，不是报错——它本来就不提供 shell。

第四章：意外收获——Windows 侧也有同一个坑

拉博客仓库时又撞了一次：Windows 上的 git pull 居然也超时了。

1

ssh: connect to host ssh.github.com port 443: Connection timed out

原因一模一样：Windows 的 ~/.ssh/config 只配了 ssh.github.com:443，没配代理通道，而 Windows 的 OpenSSH 同样不认代理环境变量。

临时绕过办法：HTTPS 协议本身是吃 http.proxy 的，可以直接走代理拉取，不改 remote：

1
2
3

git -c http.proxy=http://127.0.0.1:7892 `
    -c https.proxy=http://127.0.0.1:7892 `
    pull https://github.com/iloveu521/hugo-main.git main

1
2

* branch main -> FETCH_HEAD
Already up to date.

要根治的话，Windows 侧思路相同：给 OpenSSH 配一个支持 CONNECT 的 ProxyCommand（Windows 上可以用 ncat 或 connect.exe），或者干脆给 git 全局配上 HTTPS 代理：

1
2

git config --global http.proxy http://127.0.0.1:7892
git config --global https.proxy http://127.0.0.1:7892

# 1. 确认 WSL 是 mirrored 模式
cat /mnt/c/Users/<你>/.wslconfig | grep networkingMode

# 2. 确认代理端口在监听（Windows PowerShell）
netstat -ano | findstr ":7892"

# 3. 确认 WSL 能经代理访问外网
curl -x http://127.0.0.1:7892 -I https://github.com

# 4. 确认直连 22/443 是否被墙
timeout 6 bash -c '</dev/tcp/github.com/22' || echo "22 blocked"

# 5. 确认 SSH 配置存在且含 ProxyCommand
cat ~/.ssh/config

# 6. 端到端验证
ssh -T git@github.com

三条教训

  1. 环境变量不是全局圣旨——http_proxy 只管「认它的程序」，OpenSSH 从来不在其中；
  2. 网络模式决定排查剧本——NAT 模式查 Allow LAN 和主机网关 IP，mirrored 模式直接用 127.0.0.1，两者别串台；
  3. 分层定位，别乱动 Key——卡在 Connecting ... port 22 是网络层问题，重新生成 SSH Key、折腾 ssh-agent 都是无用功。

上次栽在 Allow LAN，这次栽在 ProxyCommand。

GitHub SSH 超时这口锅，看来还能再炒好几顿。
