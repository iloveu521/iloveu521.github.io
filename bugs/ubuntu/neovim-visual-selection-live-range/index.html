Neovim 可视模式移动选区报 E20：不要在映射回调中读取旧的范围标记

Neovim Visual 模式的 Lua 映射回调中，`< 与 `> 标记可能尚未更新。记录如何用实时 v 锚点与当前光标计算选区，修复 E20: Mark not set，并补齐首尾边界测试。

2026-10-11
2 minute read
loading... 次

问题现象

为了让 Neovim 与 VS Code 使用同一套快捷键，需要在普通模式和可视模式中移动当前行或选中的多行：

1
2

vim.keymap.set('x', '<M-I>', function() move_selection(-1) end)
vim.keymap.set('x', '<M-K>', function() move_selection(1) end)

最初的 move_selection() 直接读取可视选区标记 '< 和 '>：

1
2

local first_line = vim.fn.line("'<")
local last_line = vim.fn.line("'>")

当用户刚按 V 创建一个新选区并立即触发 Lua 映射时，移动可能失败；在可复现测试中会得到 E20，选中的行没有移动。

环境信息

  • Windows 终端中的 WSL Ubuntu
  • Neovim Lua 配置
  • vim.keymap.set() 注册的 Visual 模式回调
  • 行移动使用 Ex 命令 :move
  • 自动化验证使用 headless Neovim

这个问题不依赖特定插件。多光标插件只是同一次配置调整中的其他功能，与本问题的根因无关。

错误信息 

1

E20: Mark not set

还可能出现另一种更隐蔽的表现：没有报错，但 '<、'> 指向上一次可视选择，导致移动错误的行。

排查过程

1. 先确认普通模式移动正常

普通模式可以直接使用当前光标行，并在首尾边界返回：

1
2
3
4
5

local line = vim.fn.line('.')
local last_line = vim.fn.line('$')

if direction < 0 and line == 1 then return end
if direction > 0 and line == last_line then return end

首行继续上移、末行继续下移都会像 VS Code 一样静默不操作，非边界行可以正常移动。

2. 原有测试掩盖了真实问题

最初的测试在调用回调前手动设置了范围标记：

1
2

vim.fn.setpos("'<", { 0, 1, 1, 0 })
vim.fn.setpos("'>", { 0, 2, 1, 0 })

这种测试证明了“标记存在时函数能运行”，却没有模拟用户刚进入 Visual 模式的真实时序，因此无法发现 E20。

3. 用真实 Visual 操作复现

测试改为让 Neovim 真正进入行选择模式：

1
2

vim.cmd('normal! ggVj')
move_selection_up.callback()

这时不再提前写入 '<、'>，问题稳定复现，说明错误来自选区数据的读取时机。

根本原因

'< 与 '> 表示最近一次 Visual 选区的边界。在 Visual 模式映射的 Lua 回调执行时，本次选区可能尚未写回这两个标记，所以它们可能未设置或仍保存上一次选区。

当前 Visual 选区的实时信息应来自：

  • v：进入 Visual 模式时的锚点；
  • .：当前光标位置。

因此，回调必须根据 vim.fn.getpos('v') 和 vim.fn.getcurpos() 计算本次选区，而不能假设 '<、'> 已经更新。

解决方案

先取得实时锚点和光标，再按位置排序出起点与终点：

local function move_selection(direction)
  local anchor = vim.fn.getpos('v')
  local cursor = vim.fn.getcurpos()
  local anchor_before_cursor =
    anchor[2] < cursor[2]
    or (anchor[2] == cursor[2] and anchor[3] <= cursor[3])

  local first = anchor_before_cursor and anchor or cursor
  local last = anchor_before_cursor and cursor or anchor
  local first_line = first[2]
  local last_line = last[2]

  if direction < 0 and first_line == 1 then return end
  if direction > 0 and last_line == vim.fn.line('$') then return end

  local destination = direction < 0 and first_line - 2 or last_line + 1
  vim.cmd(('%d,%dmove %d'):format(first_line, last_line, destination))

  vim.fn.setpos("'<", { 0, first_line + direction, first[3], first[4] })
  vim.fn.setpos("'>", { 0, last_line + direction, last[3], last[4] })
  vim.cmd('normal! gv=gv')
end

这里有三个关键点：

  1. 用 v 和当前光标取得实时选区；
  2. 执行 :move 前检查缓冲区首尾边界；
  3. 移动后更新 '<、'>，再通过 gv=gv 恢复选区并重新缩进。

验证结果

验证覆盖以下场景：

  • 当前行在第一行时向上移动：静默不操作；
  • 当前行在最后一行时向下移动：静默不操作；
  • 普通模式的非边界行可以上下移动；
  • 真实 V 模式选区触及首尾边界时不会报错；
  • 真实 V 模式选区可以整体上移；
  • 移动后文本顺序符合预期；
  • 完整 Neovim 配置测试与 git diff --check 通过。

关键回归测试不再手动伪造 '<、'>，而是通过 normal! ggVj、normal! 2GVj 建立真实可视选区，从而验证用户实际触发路径。

经验总结

  1. Visual 模式仍在进行时，v 和当前光标比 '<、'> 更能代表实时选区。
  2. 测试不要提前填充生产路径本应生成的状态，否则容易掩盖时序错误。
  3. 编辑器快捷键需要显式覆盖缓冲区边界；理想行为通常是静默 no-op，而不是抛出 Ex 范围错误。
  4. 对映射回调的验证应执行真实模式切换和选择动作，而不只是检查映射字符串。
